# 코드북 — LLM 에이전트 협업 실패 유형 (v1 · 2026-09-29)

각 실패 항목(익명화된 실수 로그 1건)에 아래 세 가지를 붙인다. 판단은 **그 항목이 스스로 밝힌 원인**을 기준으로 한다(나중 항목의 해석을 끌어오지 않는다).

## 1. primary — 주 실패 유형 (하나만)
| 코드 | 이름 | 정의 | 예 |
|---|---|---|---|
| F1 | 출처·맥락 딱지 오류 | 값·데이터·화면이 **어느 시스템·시점·대상**의 것인지 잘못 붙이거나 확인하지 않음 | 개발계 데이터를 운영 사실로 보고, 다른 조회의 결과를 이 조회의 근거로 씀 |
| F2 | 단위·표기 변환 오류 | 금액 배율·통화·날짜·자릿수·표기 형식의 변환을 틀림 | 원화 금액 100배 오류, 날짜 형식 |
| F3 | 검증 생략·거짓 완료 | 결과를 **다시 확인하지 않고** 완료·성공·해결을 보고함 | 저장 응답만 믿고 「고쳤다」, 업무 흐름 시험 없이 완료 보고 |
| F4 | 근거 없는 확신·추론 비약 | 확인 안 된 가설·추정을 사실처럼 말하거나 하나의 가설에 매달림 | 화면을 본 적 없이 필드 이름으로 화면 구성을 단정, 그럴듯한 이론을 문서화 |
| F5 | 기존 의도·업무 맥락 무시 | 의도된 설계·통제·업무 규칙을 버그나 불필요한 것으로 판단 | 내부통제 장치를 없애자고 제안 |
| F6 | 필수 절차·사람 관문 건너뜀 | 알려진 승인·확인·마무리 절차를 생략하고 진행 | 이름 승인 없이 전송요청 생성, 완료 체크리스트 생략 |
| F7 | 범위 이탈·과잉 행동 | 요청보다 넓게 바꾸거나 본류와 무관한 조사를 계속함 | 승인 없이 규칙까지 변경, 파생 이슈를 끝까지 따라감 |
| F8 | 기록·문서 결함 | 문서·데이터 파일을 쓰거나 고치다 생긴 결함, 기록 간 불일치 | 설정 파일 형식 파손, 번호·집계 불일치, 낡은 기록 방치 |
| F9 | 소통 결함 | 사람에게 전달하는 방식의 결함 | 너무 길거나 기술적인 답, 잘못된 발신자·소속, 확인 가능한 것을 상대에게 물음 |
| F10 | 도구·환경 조작 오류 | 도구·API·셸·연결 대상의 **기술적** 오용 | 세션을 끊는 호출, 조회문 길이 제한, 잘못된 연결 대상, 인코딩 |
| F11 | 기타 | 위 어디에도 맞지 않음(이유를 note 에 적는다) | |

구분 요령: F3는 「확인을 안 했다」, F4는 「확인 안 된 것을 단정했다」. F6는 **알려진 사람 관문**을 건너뜀, F10은 기술적 조작 실수. 연결 대상(개발/운영) 혼동으로 **값을 잘못 해석**했으면 F1, 연결 대상 선택 자체를 **잘못 조작**했으면 F10.

## 2. detected_by — 누가 실패를 드러냈나 (하나만)
| 코드 | 뜻 |
|---|---|
| user | 운영자(사람)의 지적·질문·반박 |
| third_party | 현업·타 부서 등 제3자의 제보·반박 |
| self | AI가 스스로 발견(재조회·검증 중) |
| tool | 점검 도구·훅·시스템 오류(덤프 등) |
| unclear | 항목에서 알 수 없음 |

## 3. recurrence — 재발 여부
- `yes`: 항목이 **이전에 기록된 같은 유형의 실수가 다시 일어났다**고 명시(「재발」「N번째」「같은 실수」 또는 이전 실수 번호 인용)
- `no`: 그런 언급 없음

## 출력 형식 (JSON 한 줄에 한 항목)
`{"n": 번호, "primary": "F3", "detected_by": "user", "recurrence": "no", "note": "한 줄 근거(선택)"}`
